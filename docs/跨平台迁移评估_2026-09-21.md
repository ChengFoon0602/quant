## 0. 一句话结论

**研究层迁 Linux 有真实收益，执行层（实盘）不能迁。** A 股实盘通道锁死在 Windows（见第 4 节）。所以答案是「**分层迁移 + 明确边界**」，不是「全部搬家」。

另外有一个比「迁平台」更值钱、成本更低的优化（第 2.3 节：CSV → Parquet），建议排在迁移前面。

### 1.1 迁移难度的关键判断

`requirements.txt` 的全部依赖：

```

numpy 2.1.3 · pandas 2.3.3 · scipy 1.16.3
```

**没有任何 Windows-only 包。** 全部是纯 Python 或有官方 Linux wheel 的包。这意味着**技术层面的迁移难度很低**——真正的风险不在「能不能装」，而在「装完数字还对不对」（第 7 节）。

### 2.2 逐条判断

**Python —— 研究端不换。**
生态碾压：`akshare`/`baostock` 取数、`pandas` 面板运算、`LightGBM` 训练、`matplotlib` 出图，这套组合在别的语言里没有等价替代。任何「用量化框架练手就该换语言」的说法都是本末倒置。**你的瓶颈不在这里**（见 2.3）。

**C —— 当前项目没有位置。**
唯一的真实用武之地是 tick 级/低延迟路径，而 `CLAUDE.md` 红线明确「不做高频/tick 级」（E3 节）。**为了用而用会引入内存安全风险却不换来任何收益。**

**C++ —— 同上，当前没有位置。**
将来若真要做低延迟执行，C++ 是选项之一；但 Rust 在这个场景下是更省心的选择（见下）。

**Rust —— 有两个真实用途，但都不是现在。**
1. 用 **PyO3** 写 Python 扩展，替换 profiling 确认过的 pandas 热路径。注意前置条件：**先 profile**。向量化 pandas 的瓶颈通常落在 I/O 与内存分配，不在 CPU——如果是前者，换 Rust 一点用没有，换存储格式才有用。
2. 将来做实盘时，用 Rust 写**执行守护进程与风控网关**：无 GC 暂停、单二进制部署、编译期排除数据竞争。这个场景它比 Python 和 C++ 都合适。

**Fortran —— 在量化里基本没有位置，在你的物理研究里才是。**
理由很直接：**`numpy`/`scipy` 底下就是 LAPACK/BLAS，而这些库本身就是 Fortran 写的。** 你调用 `np.linalg.solve` 时已经在吃 Fortran 的性能红利了。自己写 Fortran 只在「自研数值算法且需要极致性能」时有意义——例如大规模蒙特卡洛、数值积分、特征值求解。

**所以 Fortran 的正确归宿是 `D:\桌面文件\大三\black hole`（QNM 的 Leaver 连分数、Evans 反 Stokes），不是 `quant`。**

**OCaml —— 唯一合理位置是风控/清算的规则建模，但 ROI 不划算。**
理由见 `语言学习\环境\OCaml 与函数式编程.md` 第九节：它的强项（ADT + 穷举匹配）确实对上清算业务，但你的框架里这部分目前只有 `risk/` 六个文件、约 70 KB，用 Python 完全够。引入一门新语言去优化一个不构成瓶颈的模块，是负收益。

### 2.3 一个比换语言更值钱的优化：CSV → Parquet

`X_matrix.csv` 是 **699 MB 纯 CSV**。同样数据的 Parquet 通常是它的 **1/5 ~ 1/10**，且 `pd.read_parquet` 的解析开销远低于 `read_csv`——因为它不做文本解析，直接读二进制列存。

`.gitignore` 里已经写了 `*.parquet` 和 `*.feather`（第 13–14 行），说明这件事你早就考虑过但没落地。

**建议顺序：先做存储格式，再考虑换语言。** 前者改 `build_pit_matrix.py` / `select_features.py` 几行，收益立刻可见；后者要写扩展、要维护两套工具链。

⚠️ 注意：Parquet 对 `float64` 是**位精确**的，不会破坏铁律的可复现性。但切换后要重跑 golden baseline 确认因子指纹不变。

## 3. 目标架构：分层，不是搬家

```
┌──────────────── Linux（Ubuntu）────────────────┐
│  数据获取  →  因子计算  →  ML 训练  →  回测     │
│  akshare/baostock   Alpha191    LightGBM   引擎  │
│  风控与组合构建  →  本地因子挖掘  →  报告可视化  │
│  报告生成 / 可视化 / 调度（cron）                │
└───────────────────────┬────────────────────────┘
                        │  边界：目标持仓
                        │  （CSV / SQLite / HTTP，只读单向）
                        ▼
┌──────────────── Windows ───────────────────────┐
│  QMT / miniQMT 客户端（必须常开）               │
│  xtquant: xtdata（行情）+ xttrader（下单）      │
│  执行日志与成交回报回传 → 供 Linux 侧对账        │
└────────────────────────────────────────────────┘
```

**关键设计原则：边界要先定义，再迁移。** 边界只需要传「目标持仓」这一件事，用最简单的形式（一个约定格式的文件或一张 SQLite 表）。不要在早期引入消息队列或微服务——那正是你 `docs/实施计划_2026-09-09` 里已经否决过的方向。

## 4. 实盘通道的硬约束（决定性）

**A 股主流量化实盘通道 QMT / miniQMT（迅投）官方仅支持 Windows**，无 macOS / Linux / 手机版本。Linux/macOS 用户只能通过 **Windows 虚拟机或云 Windows 服务器**运行。

原因不是技术做不到，而是路径依赖：

| 层面 | 说明 |
|---|---|
| 接口形态 | 券商柜台系统的行情/交易 API 是 **Windows DLL/EXE** 封装（用 COM、命名管道、消息循环、IE 内核界面）；供应商没有编译 Linux 的 `.so` |
| 监管报备 | 程序化交易报备要登记「终端物理特征码 + **操作系统版本号**」。换 OS 需要重新走审批，券商没有动力维护第二套报备与风控脚本 |
| 生态成本 | Linux 发行版众多、架构分裂，底层依赖 C++ 扩展/行情驱动/证书驱动，跨平台要重编、重签、重做安装包 |
| 用户体验 | 活跃量化用户绝大多数在 Windows，长期跑实盘的机构也普遍租 Windows 云主机 |

**三个必须知道的实操约束：**

1. **QMT 是本地运行，不是云端托管。** 电脑关机、休眠、断网，策略立即停止。**所以实盘绝对不能跑在你笔记本上的虚拟机里**——笔记本合盖就完事。需要一台常开机器或云 Windows 服务器。
2. **`xtquant` 通过本地 TCP 连接 miniQMT 进程**，所以那个 Windows 环境必须是「一直在跑」的。
3. **权限门槛**：QMT 不能自助下载，必须券商开通量化交易权限，多数券商要求 20 日日均资产 10~50 万、风险测评 C4 以上、签署程序化交易协议并完成监管报备（审核 1–3 个工作日）。另外**港股通标的不支持 QMT 交易**。

> 上述为券商与平台的公开口径。各家券商细则不同，**落地前请与你的客户经理确认并留存文字记录**。

**结论：实盘这一层留在 Windows。** 这不是妥协，是约束。

## 5. 迁移方案（分阶段，每阶段有验收标准）

| 阶段 | 动作 | 验收标准 |
|---|---|---|
| **P0 建立对照基线** | 在 Windows 上跑 `pytest`、`tests/factor_golden_baseline.py`、并保存一批策略的 `summary.json` | 基线存档完成，**数字已落盘**（这是迁移的唯一裁判） |
| **P1 环境** | Ubuntu 装 Python 3.12；`pip install -r requirements.txt`（严格按 pin，不用 `pip install -U`） | `pip freeze` 与 `requirements.txt` 逐行一致 |
| **P2 数据** | **复制** `data/cache*`（721 MB）+ `data/cache_meta/` + `data/manifest.json` | 跑 `from data.manifest import verify_manifest` → `drifted`/`missing`/`new` **三个列表都为空** |
| **P3 代码** | 用 `tar` 打包传输，**不要 `git clone`** | 文件字节数与 Windows 侧一致 |
| **P4 验证** | 跑全套测试 + golden baseline + 重跑一个策略报告 | 因子 hash 一致；回测指标在容差内（见第 7 节） |
| **P5 双轨切换** | 日常研究转 Linux，Windows 保留可运行副本一段时间 | 一个完整研究周期（如一次月度调仓）在 Linux 上跑通 |

### 5.1 为什么「复制数据」而不是「重新拉取」

`CLAUDE.md` 铁律 3.6 把 `manifest.json` 定义为**数据层快照锚点**。而数据源（baostock / akshare）**会修正历史数据**——复权因子调整、财务数据更正。

重新拉取 = 拿到一份「今天的数据」，它**不等于**你所有历史结论所依据的那份数据。这样迁移后即使数字变了，你也无法区分是「平台差异」还是「数据变了」——**两个变量同时变，问题就不可能定位。**

复制缓存可以把「数据」这个变量钉死，让 P4 的对比只反映平台差异。

### 5.2 关于虚拟机形态的一个提醒

`data/cache/` 与 `strategies/*/X_matrix.csv` 合计约 1.4 GB。如果你的 Ubuntu 是通过**共享文件夹 / 挂载 Windows 分区**访问这些文件，读取会明显变慢（跨文件系统的转发开销）。

具体到这个 699 MB 的 CSV，建议**放进 Linux 自己的文件系统**（如 `~/quant/`），不要长期放在 `/mnt/` 之类的挂载点上。

> 顺带一提：如果目标只是「用 Linux 工具链」而不是「要一台独立的 Linux」，**WSL2 通常比传统虚拟机更划算**——它直接共享宿主网络（第 3 节的 Linux↔Windows 边界会变得非常简单），文件 I/O 性能也更接近原生。但我无法从当前环境检查你的 WSL 状态（`wsl.exe` 被沙箱策略拦截），需要你自己确认。
> 注意：即使走 WSL2，**跨 `/mnt/d` 的 I/O 依然慢**，数据仍应放在 WSL 内部文件系统。而且 WSL 同样**不能**承担实盘——宿主机休眠就停。

## 7. 风险清单

| 风险 | 机理 | 现象 | 对策 |
|---|---|---|---|
| **浮点结果不一致** | `numpy`/`scipy` 的 OpenBLAS 线程数与 CPU 指令集派发在两边可能不同；`LightGBM` 的直方图并行累加顺序随线程数变化 | golden hash 不一致；OOF 预测小数点后若干位差异 | 基线用 `num_threads=1` / `n_jobs=1` 跑；**分层比较**：因子层要求比特级一致，模型层给容差 |
| **数据漂移** | 数据源会修正历史复权价与财务数据 | `verify_manifest()` 报 `drifted`；回测数字变化 | **复制缓存，不重拉**（5.1 节） |
| **大小写敏感** | Linux 区分大小写，Windows 不区分 | `from Data import ...` 在 Windows 能跑，Linux 报 `ModuleNotFoundError` | 迁移后跑一次全量 import；`pytest --collect-only` 能提前暴露 |
| **中文文件名 / locale** | 仓库里有 `event_study_基本面.csv`、`收益成本口径统一论证.md` | locale 未设 UTF-8 时文件找不到或乱码 | VM 设 `LANG=zh_CN.UTF-8`（或 `C.UTF-8`）；`locale -a` 确认；Python 侧 `sys.getfilesystemencoding()` 应为 `utf-8` |
| **时区** | VM 默认可能是 UTC | 日期截断偏一天 → T+1 对齐错、PIT 判定错 | `timedatectl set-timezone Asia/Shanghai`；迁移后跑 `test_monthly_sampling.py` |
| **换行符 CRLF/LF** | Git 在 Windows 默认可能 `autocrlf=true` | 经 git 传输的文本文件行尾被改写 | 数据文件**不走 git**（已在 `.gitignore` 中），用文件复制；代码用 `tar` 传 |
| **数据源接口行为** | `akshare`/`baostock` 依赖远端接口 | 拉取失败或字段变动 | P2 后立刻跑一次 fetcher 冒烟测试 |
| **虚拟机的资源争抢** | VM 与宿主共享 CPU/磁盘 | 训练与回测变慢 | 给 VM 固定核数与内存；避免把数据放在共享挂载点 |

### 7.1 关于「浮点一致性」的务实处理

**不要期望跨 OS 做到比特级一致。** 线程并行归约的加法顺序不同，末位差异是正常的。

建议分层设标准：

- **因子层**（`factor_hashes.json`）：应当一致。若不一致，说明真有问题（大小写、时区、数据），不是浮点噪声。
- **模型层**（LightGBM OOF）：允许相对误差，例如 `1e-9` 量级。若差异到 `1e-3` 量级，那就是训练过程真的不同了，要查。
- **指标层**（夏普、回撤）：允许 `1e-6` 相对误差。

**关键是要在 P0 就把这个容差写下来**，否则 P4 面对差异时你会没有判断依据——这又会变成「调参拟合错误世界」的翻版。

## 8. 建议的执行顺序

1. **先做 CSV → Parquet**（2.3 节）。成本低、收益立刻可见，且不需要跨平台。
2. **P0 建基线**，把对照数字落盘。
3. **走 P1–P4 验证迁移**，不改任何策略逻辑，只验证「数字没变」。
4. **再决定实盘**。实盘的前提是：① 券商权限已开通；② 一台常开的 Windows（不是笔记本 VM）；③ 第 6 节的规范修订已完成。
5. 新增因子挖掘直接在 Linux 上做，不要先在 Windows 写再迁。
   （注：WorldQuant BRAIN 是浏览器平台，与本地 OS 无关，不构成迁移的理由或阻碍——详见附一。）

### 明确不建议做的事

| 事项 | 理由 |
|---|---|
| 把框架重写成 Rust / C++ | 你的瓶颈在存储格式与 I/O，不在 CPU。重写会破坏 28 个测试文件构成的确定性保障，收益为负 |
| 为清算/风控引入 OCaml | `risk/` 只有 ~70 KB，不构成瓶颈，引入新语言是净成本 |
| 用 Fortran 写数值内核 | `numpy` 背后已经是 LAPACK/BLAS。留着给 QNM 项目 |
| 把实盘放进笔记本上的虚拟机 | QMT 本地运行，休眠/断网即停 |
| 在 Linux 上重拉数据 | 会同时改变「平台」和「数据」两个变量，问题无法定位 |
| 一次性全量迁移 | 迁移的价值在于「数字没变」，一次改一件事才验证得动 |

## 附一：WorldQuant BRAIN 与本地框架的关系

> **更正说明**：本稿初版把 BRAIN 当作「需要在本机写的因子挖掘代码」，并把「因子挖掘练习线」放进了第 3 节的 Linux 研究层——**这是错的**。
> WorldQuant 官方新闻稿明确说明 BRAIN 是 **web-based simulation platform**：浏览器 + 账号即可使用，**与本地操作系统无关**。因此它对「迁移 Windows → Linux」这个决定**没有任何影响，既不构成理由也不构成阻碍**。

不过它与本地框架之间确实存在一个需要提前想清楚的接口问题——**而这个与 OS 无关**，所以仍然值得写在评估稿里。

### 1. Alpha 是平台自有 DSL，不是 Python 代码

BRAIN 上的 alpha 用平台自己的表达式语言在网页 IDE 里编写与提交，不是 pandas 代码。这意味着**BRAIN 里挖出的因子不能直接搬进 `signals/`**——必须重写为本地实现（例如转成 `signals/alpha191/factors.py` 那种向量化写法）。

这一步是纯人工翻译，而**翻译过程本身就是引入偏差的地方**：DSL 里一个算子的隐含语义（窗口对齐、缺失值处理、极值截断）很容易在重写时被改掉。

### 2. 更关键的是口径不同——这正是铁律 E3 的领域

BRAIN 的模拟口径与本地框架的口径几乎每一项都不同：

| 维度 | BRAIN | 本框架 |
|---|---|---|
| Universe | 平台给定的市场股票池 | CSI500 / HS300 的 **PIT 历史成员**（含退市股，铁律 2） |
| 复权 | 平台内部处理 | 后复权 `adjust="1"`（铁律 3.5） |
| 成交假设 | 平台设定（delay / 撮合规则） | 当日收盘信号 → 次日开盘执行（铁律 1） |
| 成本 | 平台设定 | 双边 ≈ 0.1%（铁律 3），`risk/cost_model.py` 单一真源 |
| 中性化 / 截断 | 平台参数 | 本地实现（`neutralize.py` / `purify.py`） |
| 收益归属日 | 平台约定 | `pct_change()` → t→t+1 收益记 t+1（铁律 3 末） |

**结论：BRAIN 上表现好的 alpha，不代表在本地框架里有效；反过来也一样。两边的 IC / 夏普不可直接比较。**

若要把 BRAIN 的因子拿回本地验证，**第一步不是写代码，而是先把上表逐项对齐**——也就是 `docs/回测语义对照表.md` 正在做的事。这是铁律 E3 那句「语义错位时调参是在拟合一个错误的世界」的直接应用。

### 5. 补充：α 到底用什么语言写？FEL 装不了，但 Python 可以当运输层

**α 的语言是 FEL（Fast Expression Language），平台专有，无法也不需要本地安装。**

提交 α 的请求体里，`settings.language` 字段固定为 `'FASTEXPR'`，这就是它。它不是可下载的编译器或运行时——它活在 BRAIN 的网页 IDE 与服务端编译器里。类比：Excel 公式、SQL、正则表达式，你不会「安装」它们。

所以「两个系统都没装」在事实层面成立，但**这不是环境缺口，是本来就不存在的东西**。

**例外在自动化层**：BRAIN 有一套 REST 接口（`https://api.worldquantbrain.com`，与网页端 `platform.worldquantbrain.com` **不同域**），社区有成熟的 Python 封装（如 PyPI 上的 `wqb`）。流程是：

```
Basic Auth（邮箱+密码）→ POST /authentication 换 JWT
                      → POST /simulations 提交 α
                      → 从响应 Location 头取 URL 轮询
                      → 取回 Sharpe / fitness / turnover 等指标
```

**关键理解：Python 在这里是「运输层」，不是 α 语言。** α 表达式本身仍是 FASTEXPR 字符串；Python 负责批量生成、提交、轮询、落库（社区常见做法是把 `alpha_id` / `location_id` / 指标存进 SQLite）。

**因此，本节第 1 小节的结论要拆成两件事：**

| 环节 | 能否自动化 |
|---|---|
| **因子逻辑的翻译**（FEL 表达式 → 本地 pandas 向量化实现） | ❌ 只能人工。这是语义工作，不是格式转换 |
| **结果的搬运**（α 表达式文本、指标、模拟结果） | ✅ 技术上可用 Python 自动（前提见下） |

也就是说，Python 反而是 BRAIN 与本地框架之间最现实的桥——**而这与迁移决策依然无关**，Python 在两边都有。
